# موتور مشترک تنظیمات داشبورد

## هدف

فاز ۳ تنظیمات نمایش داشبورد مدیرعامل، مدیر فروش، سرپرست، کارمند و مدیر واحد را در یک موتور مشترک قرار می‌دهد. این تنظیمات فقط ظاهر و رفتار نمایش را کنترل می‌کنند و محل ورود اعداد کسب‌وکار نیستند.

## اجزا

- `core/DashboardModule.php`: ایجاد idempotent جدول و تعریف ویجت‌های هر دامنه
- `lib/DashboardPreferences.php`: خواندن، ادغام، اعتبارسنجی، ذخیره و render مشترک
- `admin/dashboard-settings.php`: فرم واحد بدون JSON برای همه دامنه‌ها
- `dashboard_widget_preferences`: ذخیره visibility، order، size، period، filters، refresh و drill-down

## منبع داده

هر ویجت یک `data_source_key` کنترل‌شده دارد. کاربر نمی‌تواند SQL، نام جدول یا JSON منبع را ویرایش کند. منابع جدید باید در کد ثبت شوند و ترجیحاً از Batch فعال و View گزارش خوانده شوند.

زنجیره مطلوب:

`Import validated and committed -> active batch -> reporting View -> calculation service -> dashboard widget`

## سازگاری

- routeهای داشبورد موجود حذف نشده‌اند.
- منوی تنظیمات به صفحه مشترک هدایت می‌شود.
- تنظیمات تخصصی مدیر فروش و mapping تیم سرپرست همچنان از صفحه‌های قبلی قابل دسترس‌اند.
- فیلدهای قدیمی `site_settings` و `manager_dashboard_widget_settings` برای سازگاری نگه داشته می‌شوند، اما ورود دستی ردیف‌ها در جریان عادی غیرفعال است.
- صفحه قدیمی مدیرعامل فقط با `?legacy=1` و برای super admin در دسترس است؛ هیچ داده یا جدول قدیمی حذف نشده است.
- داشبورد مدیرعامل، مدیر فروش و سرپرست از renderer مشترک برای ترتیب، اندازه، عنوان و visibility ویجت‌ها استفاده می‌کنند.
- empty state داشبورد مدیر فروش در نمای canonical فقط کاربران دارای مجوز Import مرکزی را به `import-center.php?source=sales_aggregate` هدایت می‌کند؛ Importer قدیمی فقط در گزارش legacy باقی مانده است.

## دامنه داده سرپرست

گزارش سرپرست ابتدا از `vw_active_sales_aggregate_rows` خوانده می‌شود. تطبیق با اعضای تیم به‌ترتیب زیر است:

1. `employee_no` کاربر با `visitor_code` منبع فروش
2. نام کاربر فقط وقتی شناسه پرسنلی ندارد

این ترتیب مانع ورود فروش فردی با نام مشابه ولی خارج از تیم می‌شود. در نبود View فعال، مسیر قدیمی فقط برای سازگاری خواندنی باقی می‌ماند.

## امنیت

- دسترسی هر دامنه با permission موجود بررسی می‌شود.
- POST به CSRF نیاز دارد.
- کلید ویجت، اندازه، دوره، refresh و filter mode با whitelist کنترل می‌شوند.
- دوره پیش‌فرض در اولین ورود داشبورد سرپرست اعمال می‌شود و refresh انتخاب‌شده از طریق renderer مشترک اجرا می‌شود.
- حالت فیلتر فقط می‌تواند داده را در دامنه مجاز نقش محدودتر کند و هرگز مجوز سرور را گسترش نمی‌دهد.
- `settings_json` و `default_filters_json` در UI نمایش داده نمی‌شوند.
- ذخیره در transaction انجام و در audit log ثبت می‌شود.

## دیتابیس

تغییر فقط افزایشی است. هیچ `DROP`، `TRUNCATE` یا حذف داده‌ای وجود ندارد. repair پیش‌فرض‌ها را upsert می‌کند و تنظیم کاربر را بازنویسی نمی‌کند.

## اعتبارسنجی نصب تازه

مسیر مشترک نصب و seed روی MariaDB ایزوله اجرا شده است. اجرای دوباره seedها duplicate ایجاد نکرد، همه تنظیمات پیش‌فرض داشبورد ساخته شدند و داده عملیاتی فروش/خرید/موجودی/تردد خالی ماند. نمایش عدد واقعی همچنان به Import معتبر، Commit کنترل‌شده و Batch فعال نیاز دارد.
